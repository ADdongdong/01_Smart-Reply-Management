## 用户需求

1. 现有入口名「填写回函资料」不直观 —— 该弹窗内实际填写的是**回函的快递/物流信息**（快递公司、运单号、发件人、收件人、寄件与签收时间，共 12 项字段中 11 项属此类），需要换成贴合内容的名字。
2. 回函快递信息与回函结果这两处数据**一旦提交后，界面再无入口可查看与修改**（进入「待填写回函结果」后快递信息入口消失，进入「已完成」后两个入口全部消失），需要补上修改入口，因此这两个操作入口需要常驻保留。

## 产品概览

回函管理列表的操作区由「按进度变化的单一主按钮」调整为「**两个常驻业务入口 + 按进度高亮**」：无论函证处于待确认、待填写还是已完成阶段，业务人员都能随时打开「回函快递信息」与「回函结果」查看并修改已填内容；同时保留原有的「下一步该做什么」引导 —— 当前该做的那一个入口以主色高亮。无风险件的一键确认与批量确认继续保留。

## 核心功能

- **入口更名**：原「回函资料录入」统一改为「**回函快递信息**」，弹窗标题、列表入口、回函进度文案、需求文档同步为同一口径。
- **两个常驻入口**：操作列固定显示「回函快递信息」「回函结果」两个入口，不再随进度隐藏；当前该做的那一个以主色高亮，其余为普通文字链接。
- **修改已填写信息**：已确认过的内容可重新打开修改并保存；修改**不改变回函进度、不重复产生人工核验留痕**，但会记录**修改人与修改时间**，并在列表中可查。
- **修改后状态规则**：已完成归档的函证允许修改，修改后仍保持「已完成」状态。
- **上次填写值回显**：重新打开弹窗时显示上次保存的值（不再退回 AI 默认值），已确认过的字段不再标记为「待确认」。
- **下一步引导不丢失**：处于「待确认」阶段时，「回函结果」入口不可用并说明原因（必须先确认回函快递信息），避免跳过核验确认环节。
- **快速通道保留**：无风险件仍可一键确认（含勾选多条批量确认），其位置与高亮入口协调，不产生两个并重的主色按钮。

## 技术栈

沿用现有栈，不引入任何新依赖：React 18 + TypeScript + Vite + Ant Design 5（原型，dev server 端口 5178）；状态由 `AppStore`（`useReducer` + Context）承载；mock 数据在 `src/mock/confirmations.ts`；文案与规范文档在 `docs/需求文档.md`。视觉延续**单一靛蓝色系**（红绿仅作状态标签），不引入新色相。

## 实现方案

### 一、命名统一（只在用户可见文案与文档层改，标识符保持稳定）

将「回函资料」口径统一为「**回函快递信息**」：

- 弹窗 `title`：`回函资料录入` → `回函快递信息`（仅改用户可见文案）
- 列表入口 label：`回函快递信息`
- **回函进度枚举随之改名**：`ReplyProgress` 的 `'待确认回函资料'` → `'待确认快递信息'`（7 字，与现有 `'待填写回函结果'` 等长，不引入列宽风险；且模块上下文已隐含"回函"）。
- 选择改枚举而非"保留旧进度名 + 靠提示关联"的原因：进度列是用户在列表里读到的第一处状态文字，若入口叫「回函快递信息」而状态叫「待确认回函资料」，正是用户本次抱怨的同一类不一致。
- 改名是**类型安全**的：`ReplyProgress` 是字面量联合类型，任何遗漏的旧字符串比较会被 `tsc` 直接报 TS2367，不会静默失效。
- 代码标识符（`CONFIRM_DOC`、`ModalKind = 'doc'`）**不做全量改名**，仅补注释锚定其为「回函快递信息」的确认动作 —— 控制爆炸半径，避免牵动判定模块与文档大面积重构。

### 二、让"修改"真正生效（本轮的功能核心）

现状核实：`ReplyDocEntryModal` 与 `ReplyResultModal` 的表单字段都是**组件内局部 state**，提交时 `dispatch({ type: 'CONFIRM_DOC' })` / `SUBMIT_RESULT` **不带任何 patch** —— 即字段值从未写回记录。因此本轮若只补入口，用户点开看到的仍是 AI 默认值，"修改"是假的。必须补齐**写回链路**：

1. **记录结构扩展**（`ReplyRecord`）：新增 `expressInfo?: ExpressInfo`、`resultInfo?: ReplyResultInfo`、`lastEditedBy?`、`lastEditedAt?`；`expressInfo` 承载快递信息 12 项，`resultInfo` 承载结果填写的人工判断项。
2. **回显优先**：`buildPrefillFields(record)` 改为「AI 默认值打底 + `record.expressInfo` 覆盖同名 key」，且已被人工保存过的字段 `adopted: true`、`source` 标注为"人工确认值"——重开弹窗即显示上次保存值，且不再被标为待确认。`ReplyResultModal` 同样以 `record.resultInfo` 初始化 `matched / diffDesc / sealConsistent / sealReason / officialSeal / crossSeal`。
3. **两种语义、两个动作**：

- 首次确认（`verifyStatus === 'pending'`）：沿用 `CONFIRM_DOC`，改为**带 patch** —— 同时写入 `expressInfo`、打核验留痕、进度推进到「待填写回函结果」、衔接结果填写（语义完全不变）。
- 编辑态（`verifyStatus === 'verified'`）：新增 `UPDATE_DOC { recordId, patch }` —— 只写 `expressInfo` + `lastEditedBy/At`，**不动 `replyProgress`、不重新写 `verifiedBy/verifiedAt`**（避免"同一件事两处签字"，也不必让用户与既定留痕规则产生歧义）。
- 结果侧同理：归档用 `SUBMIT_RESULT`（带 patch）；编辑态用新增 `UPDATE_RESULT { recordId, patch }`（保持「已完成」）。

4. **列表状态判定**：编辑态由 `record.verifyStatus` / `record.replyProgress` 单点判断并下传给弹窗，弹窗内不自行猜测。

### 三、操作列新形态（`ReplyList.tsx`）

去掉"按进度变化的单一主按钮"，改为两个常驻入口，**可点性用 `disabled` + `Tooltip` 而非隐藏**：

| 行的状态 | 第一个位置 | 回函快递信息 | 回函结果 | 其余 |
| --- | --- | --- | --- | --- |
| 待确认快递信息（有风险） | — | 高亮（下一步） | 不可用（Tooltip：请先确认回函快递信息） | AI 核验 · 查看 · 删除 |
| 待确认快递信息（无风险件） | 一键确认（主色 + ThunderboltOutlined） | 普通链接 | 不可用（同上） | AI 核验 · 查看 · 删除 |
| 待填写回函结果 | — | 普通链接 | 高亮（下一步） | AI 核验 · 查看 · 删除 |
| 已完成 | — | 普通链接 | 普通链接 | AI 核验 · 查看 · 删除 |


- 关键约束：**「回函结果」在「待确认快递信息」阶段必须不可点**。因为 `SUBMIT_RESULT` 会把 `verifyStatus` 置为 `verified`，若允许从该状态直接进结果弹窗，等于绕过「确认回函快递信息」这一唯一留痕入口（审计底线）。
- 高亮与一键确认不并重：无风险件把主色让给「一键确认」，此时「回函快递信息」降为普通链接（其下一步动作已由一键确认代表），避免两个主色按钮同时出现。
- 布局预算：入口由 4 个增至 5 个（无风险件行 6 个），操作列 `width` 由 216 调至约 296，表格 `scroll.x` 由 1240 同步上调；验证阶段截图确认未挤压其他列。

### 四、留痕与提示（对用户选定的"保持已完成"做轻量补强）

用户选定"已完成行修改后状态保持已完成"。实现时补一条**轻量修改留痕**：`lastEditedBy / lastEditedAt`，呈现位置（不新增列，避免表格变宽）：

- 两个弹窗底栏提示：编辑态显示「该函证已归档，本次修改将更新数据并保持『已完成』状态；系统会记录修改人与修改时间」
- 列表**展开行**的核对型字段区追加一行「最近修改」（无修改记录显示「—」）
- 保存成功用 `message.success` 反馈，文案含修改人

## 实现要点（执行注意）

- **不并行编辑同一文件**（本项目曾因并行编辑丢失改动）：本轮 `src/types/index.ts`、`src/pages/ReplyList.tsx` 会被多个步骤触及，必须按 todo 顺序串行推进。
- **审计底线**：AI 只产出建议与风险标签、绝不自动落库；核验留痕的唯一入口仍是「回函快递信息」弹窗的**首次确认**；编辑态不重复留痕。
- **编辑态不得改动进度**：已确认后再次保存若误走 `CONFIRM_DOC`，会把进度从「已完成」退回「待填写回函结果」——这是本轮最容易引入的回归，需在实现与验证中都单点确认。
- **性能**：`quickMap` 已是整表算一次再查表（上轮完成），本轮不新增逐行重算；`buildPrefillFields` 仅在弹窗挂载时调用一次，编辑写回为 O(1) 次数组 `map`，无额外开销。
- **mock 演示数据**：确保至少保留一条「已完成」记录用于演示"已完成行 → 打开两个入口 → 修改并保存 → 状态仍为已完成 + 出现最近修改留痕"的完整链路。

## 关键代码结构

```ts
/** 回函快递信息 —— 该弹窗承载的 12 项字段（11 项为快递/物流信息） */
export interface ExpressInfo {
  replyFile?: string
  faceSheet?: string
  expressCompany?: string
  expressNo?: string
  senderName?: string
  senderPhone?: string
  senderAddress?: string
  receiverName?: string
  receiverPhone?: string
  receiverAddress?: string
  sendTime?: string
  signTime?: string
}

/** 回函结果填写 —— 由人工做出的判断项（AI 仅给建议） */
export interface ReplyResultInfo {
  matched?: boolean
  diffDesc?: string
  sealConsistent?: boolean
  sealReason?: string
  officialSeal?: boolean
  crossSeal?: CrossSealChoice
}

/** 编辑态动作：只写内容与最近修改留痕，不改变 progress、不重打核验留痕 */
export type EditAction =
  | { type: 'UPDATE_DOC'; recordId: string; patch: { expressInfo: ExpressInfo } }
  | { type: 'UPDATE_RESULT'; recordId: string; patch: { resultInfo: ReplyResultInfo } }
```

## 架构说明

沿用现有分层，不新增模式：**列表页单一互斥弹窗状态（`activeModal`）→ 弹窗（受控模式）→ store action（唯一写入出口）**。本轮变化集中在"入口常驻化 + 编辑态写回"两点，均为现有链路的延伸：写入仍全部经 store reducer，未新增旁路；`ModalKind` 仍为 `'view' | 'verify' | 'doc' | 'result'` 四类，不新增弹窗种类。
