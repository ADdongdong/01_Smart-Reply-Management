## 核心业务规则（不可违背）

1. **「回函结果是否相符」由印章落章区域决定**，不是用户主观填写：
   - 印章落在「信息证明无误」区 → 相符
   - 印章落在「信息不符」区 → 不相符
   - 该规则同时决定「函证结果是否相符」与「盖章是否与被询证方名称一致」两个字段的 AI 建议值
2. **银行函证唯一标识一封函证的四要素**：银行名称 + 被审计单位名称 + 函证起始日期 + 函证截止日期
3. **往来函证**回函是我方发出、右上角带系统二维码，按二维码切分与归属；**银行函证**回函由银行自行制作、无系统标记，只能按四要素匹配
4. **一个函证控制表内的函证类型必须一致**：要么全是往来函证，要么全是银行函证，不会混排。（银行函证流程已于 2026-09-17 v2.5 细化完成，见下方「银行函证归属匹配规则」）
5. **一个函证可能发函多次、回函多次**。每次发函对应一条「发函记录编号」；列表中展示**最近一次发函**的编号，历次编号收进展开行
6. **往来函证二维码编码的是「函证编号」，不是「发函记录编号」**（2026-09-15 用户确认）—— 系统只能判断「这份回函属于哪封函证」，判断不出是第几次发函，因此**归属落点是函证**，无需人工区分次数
7. **列表行粒度 = 一封函证一行**（v2.1 起，**取代** v2.0 的「一次发函一行」）：行主体是函证，行上呈现该函证**最近一次回函**的数据；「回函次数」列显示次数，≥2 次可点击展开历次回函
8. **重复回函以最新一次为准（最终有效回函）**：同一函证多次回函时，**回函时间最新**的那条为「最终有效」；历史回函标「已被覆盖，可不处理」，其回函资料与结果**非必填**、风险不提示、**不计入统计**，但保留查看与 AI 核验留痕。该判定**按回函时间自动推导**，不引入状态字段、不人工标记
9. **回函管理列表只含「已回函」的函证**：表单初始为空，只有【上传回函文件】成功匹配到函证的数据才进入；**未回函的函证由「未回函管理」模块承载**
10. **回函进度 = 用户视角的「下一步动作」，共 3 态**：`待确认快递信息` →（确认）→ `待填写回函结果` →（保存）→ `已完成`；**不存在「未回函 / 待识别」**。**进度表达的是「下一步待办」，不是「数据是否锁定」** —— 三个状态下都可重新打开两个业务入口查看与修改已保存的内容（v2.19 新增规则 R-07）
11. **统计行口径**（主操作行右侧）：`共 N 条 · 待人工确认 X · 已完成人工确认 Y`。N = **函证数**（列表行数）；「待人工确认」= 最终有效回函的 **AI 核验结果尚未人工确认**（只看「人工核验」列）。**不再使用「待我处理 / 全部」视图切换**
12. **删除按函证删除**：连同该函证的全部回函记录一并移除；二次确认文案需说明共几次回函记录
13. **「一键确认」仍是人工动作（v2.14 内控底线）**：无风险件的快速通道只是把「开弹窗 → 逐项确认 → 再开弹窗 → 再确认」合成一次点击，**留痕照打**（核验人 + 时间 + `confirmMode: 'quick'`）；判定口径取「**只要有一个提示就不给快速通道**」（未检出骑缝章、手写区域与印章区域不一致等一律拦住），且状态层写入前逐条复校 —— 不让「AI 说没问题」成为跳过人工判断的理由
14. **快递面单不是单独上传的文件（易被误解，需对外澄清）**：面单页在回函拼接件里、单号由 AI 在识别阶段读出并与函证编号建立对应；单独导入的是快递**详细信息 Excel**（公司 / 地址 / 电话），按运单号匹配代入，属**独立可选**流程，不做步骤化处理
15. **核验留痕只有一个触发点（v2.17；v2.19 补充编辑态）**：「**AI 核验**」页**只读**（只用于查看 AI 的判断依据，底栏仅「关闭」，页内说明留痕在别处），「已人工核验」（核验人 + 时间）统一在「**确认回函快递信息**」时打一次 —— 同一件事不设两处签字，用户也就不会困惑「该点哪个入口」。**v2.19 补充**：已确认过的内容再次打开属**编辑态**，走 `UPDATE_DOC` / `UPDATE_RESULT`，**只写内容 + 最近修改留痕（`lastEditedBy` / `lastEditedAt`），不重打核验留痕、不改回函进度**
16. **回函结果页的 AI 结论是纯建议态（v2.17）**：结论条**默认不填入表单，必须人工点「采纳」才进入**（原先相符性与盖章一致性默认已等于 AI 值 = AI 自动写入，与 C-03 相悖）；必填项未处理时**保存被拦下并列出缺项**，对应区块标浅红底、按钮保持可点。当前「AI 核验结论」区块共 **5 项**：相符性 / 盖章一致性 / 是否为公章 / 是否有骑缝章 / 不相符描述
17. **入口文案口径（v2.17 定；v2.19 操作列改形态）**：入口名与「回函进度」列**同词对应**（`待确认快递信息` → 「回函快递信息」；`待填写回函结果` → 「回函结果」），不引入序号；「AI 核验」入口在**待核验且确有风险原因**时前置风险图标（已核验与无风险行不标记）。**v2.19 起操作列改为「两个常驻业务入口 + 进度高亮」，独立主按钮取消** —— 详见下方「列表操作区」（v2.19 版）
18. **回函结果的两项印章字段（v2.18）**：「**是否为公章**」（依据 = 印章识别检出的印章类型：公章 → 是；财务章等其他 → 否；未检出印章时**无法判定**）与「**是否有骑缝章**」（检出 → 是并带检出数量；未检出 → 否）**均为必填**（归档校验共 4 项必填），且同步展示在「AI 核验结论」区块。骑缝章有**三态：是 / 否 / 不适用（单页回函）** —— 单页回函不存在该概念，而**回函页数不在识别输出里**，故第三态交人工选择

## 银行函证归属匹配规则（v2.5，2026-09-17 落地）

> 银行回函由银行自行制作、**文件内无系统二维码**，无法像往来函证那样精确命中函证编号，只能按四要素定位。
> 旧表述「银行函证流程后续单独讨论」**已作废**。

**四要素权重**：银行名称 **50%**（唯一性关键判据）/ 被审计单位名称 20% / 函证起始日期 15% / 函证截止日期 15%。

**归一化（比对前统一处理）**：全角转半角、去空白与标点、繁转简、**剥离企业组织形式后缀**（股份有限 / 有限责任 / 有限公司 / 公司 …）；银行简称别名表（工行 → 中国工商银行 等）；日期兼容 `2024-01-01` / `2024/01/01` / `2024.01.01` / `2024年1月1日` / `20240101`。

**单要素命中三态**：精确命中（计满分）/ **模糊命中（计 80% 权重）** —— 覆盖分支行落款（`齐商银行张店支行` ⊃ `齐商银行`）、简称、相似度 ≥ 80% 的轻微错字 / 未命中（不计分）。

**档位判定**（唯一出口 `decideLevel`）：

| 档位 | 条件 | 处置 |
|---|---|---|
| `auto` 自动归属 | 银行名称**精确**命中且总分 = 100% | 识别完成即落库 |
| `confirm` 建议归属 | 银行名称命中（含模糊）且总分 ≥ 65% | **需人工确认**后才落库 |
| `manual` 待人工指定 | 银行名称未命中，或总分 < 65% | 候选列表人工指定 |

**写入时机（关键约束）**：**归属未确定前不写入回函管理列表**。`auto` 在识别完成时落库；`confirm` / `manual` 必须经人工「确认归属」或「指定归属」后才落库 —— 避免「归属错了但已进列表」。且**归属操作入口要等整体识别跑完（`status === 'success'`）才开放**，防止核验结果未齐就落库。写入统一收敛于 `AppStore.finalizeTask`（`applied` 标记保证原子、不重复写入）。

**归属来源留痕三态**：`自动归属`（中性灰）/ `人工确认`（主色底）/ `人工指定`（主色淡底）—— v2.8 起不再用独立色相，两档人工操作靠标签文字区分。

**银行函证专属回函结果字段**：用「**询证事项逐项核对表**」替代往来的「科目余额分录」—— 按标准《银行询证函》固定询证项（银行存款 / 银行借款 / 注销银行账户 / 委托贷款 / 担保（含保函）/ 票据贴现 / 未到期保理 / 应付票据 / 信用证 等）逐项核对，字段为 询证事项 / 发函金额 / 回函金额（可编辑）/ 差异 / 核对结论 / 备注，差异行整行标红。**相符性判定 = 印章落章区域 + 逐项核对结果**（有差异即判不相符），比往来函证多一层。

**代码落点**：算法 `src/services/bankMatch.ts`（纯函数、无随机数、可整体替换为真实接口）；看板 `src/components/BankTextRecognition.tsx`（`mode='assign'` 可操作 / `'verify'` 只读）；需求文档 6.4（字段分层）与 7.3（归属规则）。

## 核心设计原则（贯穿全部 UI）

> **AI 只产出「建议 + 风险标签 + 置信度」，绝不自动落库。所有 AI 输出必须经人工确认才写入，并留下「已人工核验」留痕（核验人 + 时间）。**

这既满足审计证据链合规，也是「标注是否人工核验」需求的由来。

## 进度 / 状态呈现的两条相反原则（易混淆，务必区分）

| 环节 | 原则 | 原因 |
|---|---|---|
| **归属匹配**等系统内部处理 | **不暴露内部步骤**（页面切分、二维码/文本定位、快递面单识别只给最终结果「归到哪封函证」） | 用户不关心系统内部怎么跑 |
| **AI 智能核验** | **必须把每个核查点列全**（回函一致性检测 / 印章识别 / 手写体识别 / 银行函证文本识别）及各自结论 | 用户需要知道 AI 到底做了哪些检查，这是审计证据链的组成部分 |

一句话：**内部实现细节不暴露，AI 的核查内容必须全暴露。**

## AI 检测点清单（识别进度按此逐行展示，共 6 项，各带独立进度条）

1. 发/回函一致性检测
2. 回函文件是否印章检测
3. 骑缝章检测
4. 印章与被询证单位名称一致检测
5. 手写体检测（银行函证替换为**银行函证文本识别**）
6. 快递面单识别

> 「归属匹配」不属于检测点，**不展示进度条**，只给结果（归到哪封函证）。
>
> **识别队列内一律不使用横向进度条**：所有状态（检测点行、批次卡片、悬浮进度卡）统一用**圆形图标**（待检测 ○ / 检测中 ⟳ / 已完成 ✓ / 失败 ✕）+ 文字计数承载。

## 界面简洁风格约定（v1.1 起，务必遵守）

- 主页面自上而下**不超过 3 层**：筛选区 → 主操作行 → 表格
- **不设页面标题行**（模块名由顶部导航高亮表达）；主操作行内只放一个**「操作指引」文字入口**（点击弹出操作指引弹窗 `OnboardingGuide`），**界面内不常驻步骤条 / 进度条**（`InlineSteps.tsx` 已删除）
- 表格使用**单行表头**，不使用分组表头行；**不使用组间竖分隔线**（v2.3 起已全部删除），分组信息由列顺序与表头文字承担；**不用色条 / 底色等颜色标注**
- 列顺序（v2.1）：被询证单位 → 函证编号 → 发函记录编号 → **回函次数** → 回函进度 → AI 风险 → 人工核验 → 操作
- **四个明细入口统一为全屏 Modal**（v2.6）：查看 / AI 核验 / 资料录入 / 结果填写 —— 由 `components/FullscreenModal.tsx` 承载（100vw × 100vh、标题栏 / 滚动内容区 / 固定底栏），列表页用**单一互斥状态** `activeModal` 驱动，**不再占用独立路由**（`/reply/:id/doc`、`/reply/:id/result` 已删）；「资料录入」确认后直接衔接「结果填写」。全屏后遮罩不可见，因此**关闭入口必须保留三处**：右上角 `×`、`Esc`、底栏按钮
- 预览区布局：查看 / 资料录入 / 结果填写弹窗的左侧函证预览为弹性主区域（回函结果填写 `flex: 1.15`、高 620）；内容区限宽 1600px 居中（`.fs-body-inner`）
- **AI 核验页左右分栏（v2.12 定稿）**：左侧常驻预览（`flex: 1.15`、高 620、默认 AI 批注）+ 主视图下方**常驻图例**（蓝框＝检出印章 / 蓝虚线＝手写区 / 绿框＝相符 / 红框＝异常或不相符 / 灰虚线＝未命中落章区）；右侧 `flex: 1` = **检测项切换（分段控件样式）**：浅底轨道（`--c-neutral-bg` + 圆角 10 + padding 4）+ 选中项**白色浮起**（`#fff` + `--shadow-card`）其余项透明，文字仅靠墨色深浅与字重区分 —— **不用描边、不用彩色字**（用户反馈「蓝色边框 + 蓝色字体很没质感」）。切换项内容 = **拟物图标 + 名称**：一致性 `AuditOutlined` / 印章 `SafetyCertificateOutlined` / 银行文本 `BankOutlined` / 手写体 `HighlightOutlined`；**不设红绿蓝状态点、不写结果摘要**（用户要求「只要展示这一项核验了什么」），仅把**有风险项的图标着红档色**。下方为选中项明细。**页面不重复函证基础信息**（标题栏已有函证编号与被询证单位，用户反馈冗余）、**不设笼统结论 Alert**（风险等级由标题栏标签表达、悬停看原因）—— 视觉重心留给「**做了哪些检测、结果是什么**」（用户明确诉求）。点选「印章识别」卡片时主视图自动切批注；**印章识别项不再内嵌第二个 PDF 预览**（同屏两个 PDF 是反模式）
- **四项核验明细统一骨架（v2.13）**：一致性 / 印章 / 手写体 / 银行文本统一为「**① 结论条 → ② 事实清单 → ③ 处理动作**」。共享组件在 `Marks.tsx`：`ResultBar`（结论条：状态图标 + **一句话结论** + 可选次要依据 + 右侧插槽）、`InfoRow`（字段行：label 132px + 值 + 补注 + 置信度胶囊）。**结论条只讲检测结果，不讲实现方式与业务规则**（禁写「minerU 解析」「四要素加权算法」「依据业务规则」这类内容 —— 那是用户反馈「看不明白」的主因）；**同一件事不重复表达**（已删：一致性的「差异明细」块、印章的「✦ AI 判定结论」块）；**动作统一沉到明细底部**（不塞进结论条）
- **预览双视图（v2.10：pdf.js 单引擎 + 多页滚动 + 缩放）**：**「原始文件」与「AI 批注」共用同一套多页画布**（`AnnotatedPdfPreview`），切换仅显隐批注叠加层、不重建 PDF —— 两视图样式 / 页面位置 / 缩放与滚动位置逐位一致，对比零闪动。按钮文案「原始文件 / AI 批注」固定预览右上角；`forceAnnotated` 锁定批注视图（印章识别用）。**浏览能力**：多页连续滚动 + 懒渲染（`IntersectionObserver`，视口前 400px 预渲染）、底部浮动工具条（−/百分比预设/＋、适应宽度、适应页面、1:1、当前页/总页数）、**Ctrl+滚轮 / 触控板捏合缩放**（普通滚轮只滚动），**默认「适应宽度」**，缩放 25%~500%、停手 260ms 后重渲染保清晰（过程中先用 CSS 拉伸）。**批注层** = 印章定位框（主色，异常红）/ 落章区域（命中按相符性绿·红、未命中墨灰虚线）/ 手写区（主色虚线），坐标 = 页面百分比 → 缩放滚动自动跟随（实测放大 1.25 倍后百分比坐标逐位不变）。KKFileView 保留备用（仅 pdf.js 不支持的格式才需启用）。
- **预览层能力边界（2026-09-18 梳理，回答用户「有什么实用限制」）**：**自研的是「预览器」，渲染引擎是第三方的 pdf.js**（未用其自带 viewer 组件，所以工具栏 / 缩放 / 懒渲染都是自己实现，好处是样式与批注层完全可控）。已知限制分三类 —— ① **要靠后端补**：批注坐标目前是手工校准的演示值（需版面分析服务）、解析走主线程（大文件会卡，生产恢复 worker）、无「导出带批注 PDF」（需服务端合成）；② **尚未支持**：只认 PDF（Word / 图片需先转 PDF 或回退 KKFileView）、**无文本层**（不能选中复制金额、不能 Ctrl+F）、无旋转、无缩略图点击跳页、已渲染页 canvas 不释放（几十页大扫描件内存偏高）、移动端双指捏合未处理；③ **有意取舍**：缩放时先 CSS 拉伸、停手 260ms 才按新比例重渲染（换流畅度，代价是缩放瞬间略糊）；批注层 `pointerEvents: none`（纯展示，不支持点选或人工加框）。
- **标注防遮挡约定（用户 2026-09-18 反馈「标签遮挡，后面不要出现这种问题」）**：同页多个标注框常互相套叠（印章就在签章栏内），标签必须**错开贴不同的角** —— 区域类大框标签贴右上外侧、印章定位框标签贴左上外侧、手写区框标签贴左上外侧、「印章落于此区」贴框下右。改完用**矩形相交检测**（遍历标签 `getBoundingClientRect` 两两判交）验证零遮挡，不要只靠目视。
- **PDF 批注渲染的性能约定**：多页渲染用 `renderedRef: Map<index, scale>` 记录每页已渲染比例，scale 变化只重渲染差集；每页 `renderTask` 存 ref 并在重渲染前 `cancel()`（pdf.js 同一 canvas 重复 render 会抛错）；`page.previous` → 用页元素 `data-page-index` 供观察器识别。**pdfjs-dist 集成要点（踩坑记录）**：① `vite.config.ts` 必须设 `optimizeDeps.exclude: ['pdfjs-dist']` —— esbuild 预构建会破坏其内部模块（报 `hashOriginal.toHex is not a function` 之类的诡异错误）；② pdf.js 6.x 依赖 ES2024 新 API，需 polyfill `Uint8Array.toHex/toBase64/fromHex/fromBase64` 与 `Map.getOrInsert/getOrInsertComputed`；③ 解析走主线程 fake worker（`import 'pdfjs-dist/build/pdf.worker.mjs'` 挂 globalThis，不设 workerPort/workerSrc），规避 module worker 打包兼容问题；④ pdf.js 6.x 的 `render({ canvas, viewport })` 用 canvas 参数，`destroy()` 在 loadingTask 上；⑤ 标注坐标按样例件 wanglai-1-SJ01YF001.pdf 校准（底部左右签章栏）
- 层级靠间距与字重表达，不靠线条与色块；不主动添加装饰性动效
- **列表操作区（v2.19 定稿，取代 v2.14 的「单一主按钮」形态）**：操作列 = **两个常驻业务入口 + 进度高亮 + AI 核验 + 查看 + 删除（二次确认）**，**全部平铺，不设「更多」下拉**。
  - **两个业务入口「回函快递信息」「回函结果」常驻、不随进度隐藏** —— 已填写过的内容随时可重新打开查看与修改（v2.19 用户诉求：此前进入「待填写回函结果」后「回函快递信息」入口就消失、进入「已完成」后两个入口全没了，**填过就再也改不了**）。
  - **当前该做的那一个用主色高亮**承担「下一步」引导，因此**不再需要独立的主按钮**：待确认 → 「回函快递信息」高亮；待填写 → 「回函结果」高亮；无风险件 → 主色位让给「⚡ 一键确认」（此时「回函快递信息」降为普通链接，**同一行不出现两个并重的主色按钮**）；已完成 → 两个都是普通链接。
  - **待确认阶段「回函结果」根本不呈现**（不是禁用）—— `SUBMIT_RESULT` 会把核验状态置为已核验，从该状态进入等于绕过「确认回函快递信息」这个唯一留痕入口。
  - 演进教训：① 先做成「主按钮 + 更多下拉」，用户截图指出菜单里重复（AI 核验外面已有、资料录入 / 结果填写与主按钮进同一个弹窗、还摆着灰掉的禁用项）；② 改为菜单差集生成后，用户仍要求「**不要更多了，直接展示查看和删除**」→ **入口不多（本场景 5 个）时优先平铺，不要为"省空间"引入二级菜单**；③ v2.19 用户又指出「填过就改不了」→ 由此确立：**动态项不能以「隐藏」的方式表达状态，该隐藏的只有「当前确实不能做」的入口，是业务入口的必须常驻**
- **无风险件快速通道（v2.14；v2.19 实测通过）**：满足「无任何风险提示 + 检测点全通过 + 全部 AI 预填字段置信度 ≥ 90% 且值不为未识别 / 待填写」时，**主色位**变为「⚡ 一键确认」—— 一次动作完成「采纳全部 AI 资料 + 标记已人工核验（记核验人与时间）+ 进度推进到待填写回函结果」，**停在列表不跳转**；支持勾选多条批量确认（二次确认弹窗列明函证编号），**有风险提示的行勾选框置灰并给悬停原因**。判定口径独立为纯函数 `utils/quickConfirm.ts`（`checkQuickConfirm` / `splitByQuickConfirm` / `buildQuickConfirmMap`），**state 层在写入前逐条复校**（内控不依赖按钮显隐兜底）；`ReplyRecord.confirmMode` 区分 manual / quick 留痕
- **回函快递信息的值回显与默认采纳（v2.14 默认采纳 + v2.19 回显优先；原名「资料录入」）**：`buildPrefillFields` 先看 `record.expressInfo` —— **有人工保存值则回显该值**，标 `source: '人工确认值'` / `confirmed: true`（字段行显示「人工确认」标签，顶部提示「已回显 N 项上次确认值」）；否则**按置信度决定 `adopted` 初值**（≥0.9 预采纳；低于则留待人工；AI 识别不了的收件人三项始终人工），顶部明示「已自动采纳 N 项，M 项待你确认」，底栏提示必填未处理项（**只提示不阻断**）。字段底色只标「需要你处理」的项（低置信度红档 / 未识别中性），已采纳不再上色（避免整片浅底破坏单色系）。**未识别 / 未填写的项不写入 `expressInfo`**（否则「—」会被当成有效的人工确认值存下来，重开又被显示为已确认）
- 每屏只强调一个主操作；空状态必须给出唯一明确的下一步动作
- 判断依据：**用户认为「层太多 = 难用」**，任何新增区块前先自问能否合并进已有层

## 设计令牌约定（`src/theme.ts` + `src/styles/global.css`）

- **色彩：单一色系 + 红绿状态标签（v2.8，用户明确要求「统一一个色系」）**：全站只有靛蓝 `#3B5BDB` 一个色相 —— 主操作 / 链接 / 当前态 / **AI 产出** / **人工核验留痕** / 一般提示全部由主色的深浅档承担；**红 `#E5484D` 与绿 `#3FA34D` 只出现在「风险 / 相符」两类状态标签上**
- **「结构 / 机器产出 / 状态」三分法**（判断用色的唯一标准）：结构分类（卡片、函证类型标签、归属来源「自动」、命中要素标签）→ 中性灰阶；机器产出（AI 建议 / 结论 / 置信度胶囊 / 手写转录 / AI 批注框）→ **主色浅档**（不另设色相，靠「主色浅底 + 虚线框 + `✦ AI` 前缀 / `AI xx%` 胶囊」识别）；状态结论 → 红 / 绿
- **已废弃的 4 个色**：AI 紫 `#7C4DFF`（并入主色）、中风险橙 `#E8892B`（**视觉并入红档**；数据层 `riskLevel: 'medium'` 保留，档位差异由标签文字「高风险 / 中风险」表达）、人工核验蓝 `#1677FF`、AI 青 `#13A8A8`
- **底色只用 8 个变量**：`--c-neutral-bg` / `--c-primary-bg` / `--c-ai-bg`（主色淡档）/ `--c-risk-high-bg` / `--c-risk-low-bg` / `--c-tag-bg` / `--c-preview-bg`；**禁止再写 `rgba(...)` 散值或硬编码色值**（原先有 0.04~0.14 共八个透明度档，页面发花且改名时必漏改）
- **`Alert` 已全局去边框**（`.ant-alert { border: none }`，15 处使用，原是页面上「框」的最大来源）；模块级提示统一用 `.tone-block` + `.tone-{neutral|ai|primary|risk|ok}`（**无边框**，靠浅底表达；`.tone-warn` 橙色档已随配色收敛删除）；`themeConfig.colorWarning` **已重映射到风险红** —— 不改这个，antd 内置 Alert / Tag / Badge 会继续漏出橙色
- **去线条化原则（v2.3，用户明确反馈「线条过多 = 不高级」）**：卡片不用边框而用阴影；表格全表只留**表头底线**一条重线、不用竖向网格线；标签一律**浅底无边框**；嵌套区块用浅底而非第二层框；按钮分组用间距而非竖线；静态分隔统一 `--c-hairline`（`rgba(16,24,40,0.06)`）
- **阴影多层叠加（v2.4）**：`--shadow-card` 3 层 / `--shadow-hover` 4 层 / `--shadow-pop` 6 层，每层偏移与模糊成比例递减 —— 单层大模糊显脏，分层才干净
- **文字层级靠透明度而非色相（v2.4）**：`--c-text-2` = `rgba(29,33,41,0.72)`（6.4:1）、`--c-text-3` = `rgba(29,33,41,0.6)`（4.6:1，达 AA）；全页只有一个「墨色」，不要混入蓝调灰
- **缓动**统一 `--ease-out: cubic-bezier(0.16, 1, 0.3, 1)`（expo 型），并同步到 antd `motionEaseOut`
- 圆角三级：卡片 8 / 控件 6 / 标签 4；**结构性间距走 8px 网格**（页面 padding 24px）
- **主页面不超过 2 层卡片**（筛选与操作合并为一张工具栏卡 + 表格卡）；基础布局靠间距与对齐，不靠卡片拼装
- 全局 `:focus-visible { outline: 2px solid; outline-offset: 2px }` —— 键盘焦点必须可见
- **视觉风格反面清单**（营销落地页语言，工具类产品不用）：玻璃拟态、渐变、超大圆角（> 12px）、逐段滚动入场动画、装饰性动效
- **改语义色时必须全局搜一遍硬编码的 rgba**（v2.5 教训）：只改 CSS 变量会留下内联残留，导致同一页面出现「两种蓝 / 两种红」且极难察觉。搜索模式：`47,\s?91,\s?234`（旧主色）、`245,\s?34,\s?45`（旧高风险）、`82,\s?196,\s?26`（旧低风险）、`250,\s?140,\s?22`（旧中风险）
- Logo 等品牌元素用**纯色**，不用渐变（渐变属装饰，且易混用多个语义色）
- 有意保留的语义性线条：拖拽区虚线、印章定位框、落章区域高亮、手写区左侧色条、顶部导航底线、缩略图边框、高风险行左侧 2px 条
- 辅助文字 `--c-text-3` = `#6E7686`（白底对比度 4.57:1）
- **状态 / 标签文字一律墨色（v2.7，用户反馈「颜色太多 + 不要咖啡色」）**：语义色只走底色与图形元素（圆点 / 图标 / 进度条填充 / 行左标记条）；`--c-risk-*-text` 不再用于标签文字 —— 中风险深色 `#AD4E00` 呈棕调，即用户反感的「咖啡色」来源；约 20 处文字已去色，风险等级靠底色辨识
- **4px 间距栅格**（4 / 8 / 12 / 16 / 24 / 32）；禁止 6 / 7 / 10 / 14 / 20 等非栅格值
- 表格行高 38px（紧凑 32px）；圆角 卡片 6px / 标签 4px
- 字号层级 13 / 14 / 15 / 16 / 20（v2.7 整体上调一号；用户反馈原型字体偏小，与历史页面观感对齐）
- **明细弹窗布局栅格（v2.7）**：左函证文件为弹性主区域（约 55%）、右表单 label 统一 200px 右对齐，AI 建议条与表单共用同一栅格上下对齐；展开区用「浅底字段块网格」（label 灰字在上 value 墨字在下）而非 flex 平铺
- z-index 使用 CSS 变量刻度（`--z-sticky-header` / `--z-floating-card` / `--z-modal`），禁止随意写数值
- 动效仅用 `transform` / `opacity`，时长 ≤ 200ms（`--motion-fast` / `--motion-base`），支持 `prefers-reduced-motion`
- 仅图标按钮必须带 `aria-label`；当前导航项带 `aria-current="page"`

## 文件预览（pdf.js 单引擎，v2.9 起）

预览层两个视图**共用同一张 pdf.js 画布**（`AnnotatedPdfPreview`），切换按钮固定在**预览区右上角**（主色实心标识当前视图）：

- **原始文件** → 只渲染回函原件
- **AI 批注** → 同一画布之上叠加批注层（印章定位框 / 落章区域高亮 / 手写体识别区）

两者切换**不重建 PDF**（只显隐叠加层），因此样式与位置逐位一致、对比零闪动。样例 PDF 由 Vite dev server 从 `public/samples/` 以 HTTP 提供。

**印章识别面板强制批注视图**（`PdfPreview` 传 `forceAnnotated`），因为定位框是其核心输出。

**KKFileView 保留备用**（配置与组件都在 `src/config/preview.ts` / `components/KkFilePreview.tsx`）：它是第三方 iframe、无法叠加坐标标注，且自带工具栏与 pdf.js 观感不一致，故回函预览不再使用；仅当需要预览 pdf.js 不支持的格式（Word / Excel）时才重新启用。

**批注形态的技术约定（生产落地口径，2026-09-18 向用户澄清）**：AI 批注**不绘制进原文件**，而是「原件渲染层 + 批注叠加层」双层结构 —— 原件二进制保持**不可变**（审计证据链要求），批注以**结构化数据**（页号 + 归一化坐标 + 类型 + 文案 + 置信度 + 归属来源）承载，前端按坐标叠加；只有「导出 / 打印 / 归档」这类需要固定留痕的场景，才在**服务端**把两层合成为一张 PDF / 图片。这样批注可随时开关（真实文件 / AI 标注切换）、可随人工复核结论更新，同一份坐标数据也能复用到多个视图。

### 环境要点（易踩坑，务必先看）

- **不要用 Docker Desktop 的 Run 弹窗创建 kkfileview** —— 镜像未声明 `EXPOSE`，Ports 一栏填不了，容器会以「无端口映射」启动，宿主访问不到
- 宿主机 **8012 落在 Windows 保留端口区间 `7961-8060`**（`netsh interface ipv4 show excludedportrange protocol=tcp`，带 `*` 为管理员排除），Docker 无法绑定 → 改用 **18012** 映射容器 8012
- **Vite 校验请求 Host 头**，容器经 `host.docker.internal` 回访 dev server 会被拒 **403** → 需 `server.host: true` + `server.allowedHosts: ['host.docker.internal', ...]`
- kkfileview 只认 HTTP URL 并自己去下载；容器内 127.0.0.1 是容器自身，访问宿主机必须用 `host.docker.internal`
- 镜像 `latest` 实际是 **4.1.0**，配置目录在容器内 `/opt/kkFileView-4.1.0/config/`
- 调用：`/onlinePreview?url=<Base64(文件URL)>`，中文文件名先 `encodeURIComponent` 再 Base64

启动命令与全部配置集中在 `src/config/preview.ts`：

```powershell
docker run -d --name kkfileview -p 18012:8012 --restart=always keking/kkfileview:latest
```

## 工具使用注意（本机环境，2026-09-17 事故）

**写入文件后必须校验是否真的落盘**：本环境出现过 `write_to_file` / `replace_in_file` **报告成功但内容被回滚或未写入**的情况（一次是整个新建的 HTML 与目录凭空消失，一次是 `replace_in_file` 报告「新增 21 行」但文件里没有）。对策：写完立即用 `search_content`（或 `Select-String`）逐条核对关键行，不要只凭写入工具的返回值判定成功。
