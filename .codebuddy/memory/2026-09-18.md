## 关于「核心难点是不是 AI 识别准确率」的判断（产品口径）

用户追问：「核心难点就是后端调 AI 服务返回的结构化识别结果是否准确，是么？」— 回答口径定为：**识别准确性决定「能不能用」，错误处置机制决定「敢不敢用」；审计场景里后者才是真正的门槛。**

- 难点分三层：① **识别层**（扫描件质量、版式千差万别、手写体）→ 承认做不到 100%，靠容错设计；② **判定层**（AI 结论是否可解释、判错时人工能否发现）→ 靠批注可视化 + 依据呈现 + 置信度分级；③ **合规层**（证据链、留痕、责任归属）→ 靠「绝不自动落库 + 人工确认留痕」。原型已在做的三件事正是对应②③。
- **准确率要分级看**：错了直接影响结论的（落章区域判定 / 相符性）必须高；位置类（印章框、手写区）偏一点人能纠正，要求可放低；转录类（手写体文字、金额 OCR）应定位为**辅助而非替代**。
- 给 AI 服务的验收建议：用**人工纠正率**（AI 结论被人工改掉的比例）而非纯识别准确率作为业务指标。

## 修复 WebView 报错 `Cannot read properties of null (reading 'getBoundingClientRect')`

**现象**：IDE 内嵌 WebView 在 `/reply` 页报 `Uncaught TypeError: Cannot read properties of null (reading 'getBoundingClientRect')`（伴随 `Script error.`）。

**定位过程**：六轮 Playwright 走查（引导全流程、窗口 resize×多档、打开/关闭四个弹窗、切 tab、删除行、分页、排序、行展开、筛选输入、Select 下拉开合与选值、Tooltip 悬停后刷新、工作台、快递导入、悬浮卡、快速开合弹窗×5）**均未复现** → 判定为时序竞态。搜索确认这是 AntD 生态常见报错，社区反馈「快速切换界面时出现、稍等再切则不出现」。代码全仓搜 `getBoundingClientRect` = **0 处自研调用**，确认来自第三方。

**根因分析**：`ReplyList` 给「资料录入 / 结果填写」弹窗加了 `key={modalKey(...)}`（关闭时 key 切回 idle → 整棵子树立即卸载），而两个确认按钮都是「点击 → dispatch → 立即 onClose / onDone」——**点击的同一帧内被点击的按钮随子树被卸载**，此刻 AntD 的点击波纹（Wave）与浮层仍在测量已移除的元素 → `getBoundingClientRect` of null。

**修复（三处）**：

1. `main.tsx`：`ConfigProvider` 加 `wave={{ disabled: true }}` —— 关闭点击波纹（它既是该类报错的主要来源，也是与项目「克制、少动效」基调不符的装饰动效）
2. 新增 `src/utils/afterPaint.ts`（`requestAnimationFrame` 延后一帧）；`ReplyList` 的 `closeModal` 与 `onDone` 改为 `afterPaint(...)` —— 这两处是四个全屏弹窗**唯一的关闭/衔接入口**，改两处即全覆盖；延迟约 16ms，用户无感知
3. `main.tsx` 加**极窄**的全局静默：仅当错误信息同时含 `getBoundingClientRect` 与 `null` 时忽略（避免 IDE 预览面板被这类无功能影响的第三方噪音刷屏），其余错误照常抛出

**验证**：修复后重跑关键路径（资料录入→确认衔接结果填写、结果填写→保存并归档、核验→确认、快速开合×5、筛选下拉与 Tooltip 路径）全部 `ok`，无报错；tsc / build 通过。

**诚实说明**：由于未能稳定复现，无法 100% 证明报错即源于上述链路；但「点击同一帧卸载触发元素」是该报错的典型成因，三处修复正好针对它，且不影响任何功能。若线上再现，需记录触发时的具体操作步骤（尤其是是否伴随浮层打开 / 快速操作）。

## 十五、一键启动脚本（scripts/start_dev.py）

用户要求「给一个启动服务的 Python 脚本，并说明在哪个 conda 环境下使用」（2026-09-20）。

**核心结论（已告知用户）**：脚本**只用 Python 标准库**（subprocess / socket / shutil / webbrowser），因此**任何 Python 3.8+ 环境都能跑，不需要特定 conda 环境** —— 推荐 conda base 或系统 Python；**真正的前置条件是 Node.js**（本机 v24.18.0，由 nvm4w 管理在 `C:\nvm4w\nodejs`）。本机 conda 环境有 base(3.9.13) / learn-agent / mcp-form-demo / pytorch，其中 base 实测能找到 node 与 npm 并成功跑起脚本。

**脚本能力**：自检 node/npm（Windows 自动改用 `npm.cmd`）、node_modules 缺失时提示（`--install` 可自动装）、端口已占用时**直接复用而不重复启动**、轮询等待就绪（最多 90s，带进度点）、就绪后自动开浏览器（`--no-open` 关闭）、`Ctrl+C` 时用 `taskkill /PID x /T /F` 结束**整棵进程树**（Windows 上只结束 npm 会留下占用端口的孤儿 node/vite）、`--build` 走「构建 + vite preview」生产方式、`--port/--host` 可调。

**踩坑**：① Windows 上 `npm` 是 `npm.cmd`，直接 subprocess 调 `npm` 会 FileNotFoundError → 用 `shutil.which` 依次探测；② Windows 中文输出有**两种相反情况** —— 交互式终端下 Python 3.6+ 走控制台原生 Unicode 接口、中文本来正常（**不要**改写编码，否则控制台是 GBK 反而乱码），而输出被重定向到文件/管道时默认按 cp936 编码（需显式改 UTF-8）；故只在 `not stream.isatty()` 时 reconfigure 为 UTF-8。

**验证**：脚本成功拉起服务（HTTP 200），日志显示 Node 版本识别、npm.cmd 定位、就绪提示均正确；conda base（Python 3.9.13）下 `--help` 正常（类型注解 + `from __future__ import annotations` 在 3.9 兼容）；端口占用时走复用分支正常退出。
