## 第十二轮：回函管理列表的结构性重构（v2.0）

用户从「用户使用视角」提问「表上最关心哪些信息」，讨论后确定了三个前提，触发了一次结构性改造。

### 用户的三个关键回答

1. **行粒度：一次发函一行** —— 同一函证发多次会出现多行，回函挂在具体某一次发函上
2. **快捷视角：只加两个** —— 「待我处理」与「全部」
3. **核对型字段收进展开行** —— 发函方式 / 快递单号 / 回函登记日期

### 用户对「回函进度」的重要纠正

- **没有「待识别」状态**：回函管理表单**初始就是空的**，只有【上传回函文件】成功匹配到函证的数据才会进入 —— 所以不存在「待识别 / 未回函」
- **「未回函」在「未回函管理」模块**，不在本列表
- **「资料待录入」有歧义**，改为「**待确认回函资料**」（AI 已识别归档，等人工逐项确认；该步骤同时完成 AI 核验的人工确认）
- **「已完成」= 资料录入确认 + 结果填写确认**

最终状态机（3 态）：
```
待确认回函资料 →(确认)→ 待填写回函结果 →(保存)→ 已完成
```
「待我处理」判定 = `回函进度 ≠ 已完成`

### 设计认知沉淀

- **用户看列表是「扫」不是「读」**：三眼看完 —— 哪一家？什么状态？有没有红黄？
- **列序应按「用户决策顺序」而非「数据来源」排列**
- **信息分三层**：决策型（单位/进度/风险，必须首屏可见）→ 定位型（编号）→ 核对型（物流/日期，收进展开）
- **进度状态命名要用「用户下一步动作」而非「系统阶段」**
