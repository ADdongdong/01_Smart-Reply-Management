## v2.19 「回函快递信息」改名 + 已填数据可修改（需求文档同步至 v2.19）

用户两条反馈：① 「填写回函资料这个名字不够直观，回函资料里面填写的，明明是回函的快递信息」；② 「我在填写了回函资料和回函结果后，没有地方可以修改这些已经填写过的信息了，需要增加这样一个入口，所以，这两个操作按钮，可能还是得保留」。

### 一、命名口径（已全量落地）

- 原「**回函资料录入**」→「**回函快递信息**」。理由：该弹窗 12 个字段中 **11 项是快递 / 物流信息**（快递公司、运单号、发件人三项、收件人三项、寄件与签收时间），只有「回函文件」「回函封面面单」两项是文件类。
- **回函进度枚举同步改名**：`'待确认回函资料'` → `'待确认快递信息'`。选它而不是「保留旧进度名 + 靠提示关联」，是为了保住既有规范「入口名与进度列**同词对应**」—— 否则用户从列表行上看不出该点哪个。
- **改名是类型安全的**：`ReplyProgress` 是字面量联合类型，任何遗漏会被 `tsc` 报 **TS2367**。实测：一次 `replace_all` 后 tsc 直接通过，说明改动面收敛干净。
- 代码标识符**不做全量改名**（`CONFIRM_DOC`、`ModalKind = 'doc'` 保持不变），只补注释锚定语义 —— 控制爆炸半径。
- 涉及文件：`types/index.ts` / `store/AppStore.tsx` / `utils/quickConfirm.ts` / `mock/confirmations.ts` / `pages/ReplyList.tsx` / `components/ReplyDocEntryModal.tsx` / `VerificationModal.tsx` / `VerificationPanel.tsx` / `OnboardingGuide.tsx` / `docs/需求文档.md`。

### 二、两个常驻业务入口（用户选定方案）

操作列形态（**取代** v2.14~v2.18 的「按进度变化的单一主按钮」）：

| 行的状态 | 入口（按顺序） |
|---|---|
| 待确认快递信息（有风险） | **「回函快递信息」**（主色描边高亮）· AI 核验 · 查看 · 删除 |
| 待确认快递信息（**无风险件**） | **「⚡ 一键确认」**（主色实心）· 回函快递信息 · AI 核验 · 查看 · 删除 |
| 待填写回函结果 | 回函快递信息 · **「回函结果」**（主色描边高亮）· AI 核验 · 查看 · 删除 |
| 已完成 | 回函快递信息 · 回函结果 · AI 核验 · 查看 · 删除 |

四条关键设计（后续改这块务必遵守）：

1. **两个业务入口常驻、不随进度隐藏** —— 这是用户本轮的核心诉求。此前进入「待填写回函结果」后「回函快递信息」入口消失、进入「已完成」后两个入口全部消失，**填过就再也改不了**。
2. **当前该做的那一个用主色高亮**承担「下一步」引导，因此**不再需要独立的主按钮**。
3. **无风险件把主色位让给「一键确认」**，「回函快递信息」降为普通链接 —— **同一行不出现两个并重的主色按钮**。这是「动态高亮项 + 固定常驻项」并存的唯一冲突点，必须这样消解。
4. **待确认阶段不呈现「回函结果」**（不是禁用，是根本不出现）—— 因为 `SUBMIT_RESULT` 会把核验状态置为已核验，若允许从该状态直接进结果填写，**等于绕过「确认回函快递信息」这个唯一的核验留痕入口**（审计底线）。该行高亮入口的 Tooltip 说明「确认回函快递信息后可填写回函结果」。

操作列宽 `228 → 320`，表格 `scroll.x 1252 → 1344`（入口由 4 个增至 5 个）。

### 三、编辑态与留痕边界（新增规则 R-07）

- **状态语义**：已填写过的内容可随时重新打开修改；**「已完成」的行改后仍保持「已完成」**（用户明确选择）。进度表达的是「下一步待办」，不是「数据是否锁定」。
- **不重复打核验留痕**：`verifiedBy` / `verifiedAt` 只在**首次确认**时写一次。修正不是第二次确认，因此不再签字 —— 守住「同一件事不设两处签字」（v2.17 已确立）。
- **补一条「最近修改」留痕**：`lastEditedBy` / `lastEditedAt`，在列表**展开行**的「修改留痕」区块展示（不新增列，避免表格变宽）。理由：用户接受「状态不变」，但「改过却一点痕迹没有」对审计系统是硬伤。
- **状态层动作分离**：
  - `CONFIRM_DOC`（首次确认，带 patch）：写内容 + 打留痕 + 进度 →「待填写回函结果」
  - `SUBMIT_RESULT`（归档，带 patch）：写内容 + 进度 →「已完成」
  - **`UPDATE_DOC` / `UPDATE_RESULT`（编辑态）**：只写内容 + `lastEditedBy/At`，**不动 progress / verifyStatus / verifiedBy / verifiedAt**

### 四、让「修改」真正生效（本轮最容易被忽略的一环）

**发现的关键缺陷**：两个弹窗的字段都只是**组件内局部 state**，提交时 `dispatch({ type: 'CONFIRM_DOC' })` / `SUBMIT_RESULT` **不带任何 patch** —— 字段值**从未写回记录**。也就是说，如果只补入口，「修改」是假的：点开看到的仍是 AI 默认值。

补齐的写回链路：

- 新增 `ExpressInfo`（12 项）/ `ReplyResultInfo`（相符性 / 差异描述 / 盖章一致性 / 不一致原因 / 是否为公章 / 骑缝章）/ `CrossSealChoice`（在 `ReplyResultModal` 里原本是**局部类型**，已提升为共享类型）。
- `buildPrefillFields` 改为**回显优先**：`record.expressInfo` 有值则覆盖 AI 值，标 `source: '人工确认值'`、`confirmed: true`、`confidence: 1`；否则走置信度默认采纳（≥0.9）。
- `PrefillField` 新增 `confirmed?: boolean`，字段行据此渲染「**人工确认**」标签（取代 AI 置信度胶囊与「采纳」按钮），顶部摘要相应变为「**已回显 N 项上次确认值**」。
- **未识别 / 未填写的项不写入 `expressInfo`** —— 否则「—」会被当成有效的人工确认值存下来，重开时又被显示成已确认（`buildPatch` 里显式过滤）。
- `ReplyResultModal` 的表单初始值改为 `record?.resultInfo?.x`，**没有保存过时保持空白**（不默认等于 AI 建议 —— 那是 AI 自动写入，与 C-03 相悖）。

## v2.20 操作区「可预期性」改造 + 取消快速通道与批量

用户三条反馈：① 「去掉每个函证数据前面的多选框」；② 「下拉查看历次回函数据的时候，每个数据后面需要有查看，能查看历史数据，但不能修改」；③ 「取消【一键确认】按钮，现在操作部分的按钮逻辑太复杂了，我半天都没搞明白，如果是用户第一次使用，知道该怎么用。知道使用了那个按钮会有什么结果么？」

### 一、v2.19 方案被推翻（重要教训）

v2.19 我按用户当时的选择做成「两个常驻业务入口 + 进度高亮 + 无风险件一键确认」（5 个入口）。**本轮用户判定太复杂** —— 根因是**同一列里按钮因行而异**（高亮位置随进度移动、「一键确认」时有时无），业务人员建立不起稳定记忆，第一次使用更无从判断该点哪个。

**沉淀为规范（附录 B 第 12 条，v2.20 重定）**：**操作区「结构恒定」优先于「入口数量」**。三轮演进的结论：
- v2.14「主按钮 + 更多下拉」→ 用户指出菜单重复、有灰掉的禁用项
- v2.15「主按钮 + 4 个平铺」→ 用「已完成不显示主按钮」消解重复，但高亮位置在移动
- v2.19「两个常驻 + 高亮 + 一键确认」→ 用户：**我半天没搞明白**
- **v2.20 定稿**：三个位置恒定 + 主按钮承担「下一步」+ 其余收进一个下拉

**关键判断**：动态项不能用「隐藏」表达状态（v2.19 的结论）**还不够** —— 让同一列里出现位置/构成不同的按钮组合，同样会破坏记忆。**应有的做法是：位置永远不变，变的只有主按钮的文案。**

### 七、本轮踩坑（新增，务必记住）

1. **本机 `replace_in_file` 多次「报告成功但内容未落盘」** —— 本轮至少 3 处被回滚：`ReplyList` 的 `selectedKeys` 与 import、`RecordDetailModal` 的 props、`需求文档` 的第 12 条与「函证查看」标题（后者导致**出现两个 5.8**，靠搜标题才发现）。**对策：写完关键改动后必须用 `search_content` 逐条核对，不要只凭返回值判定成功**（MEMORY.md 里早有此提醒，本轮再次验证）。
2. **Ant Design 给「两个汉字」的按钮插空格** —— `修改` 渲染为 `修 改`、`查看` 为 `查 看`。因此 `has-text("修改")`、`text-is("查看")` 都会失败 → 脚本里比较按钮文案要先 `.replace(/\s+/g,'')`，或用正则 `/查\s*看$/`。
3. **表格列索引会因增删列而位移** —— 本轮去掉 `rowSelection` 列后，我原来按 `tds[5]` 读「回函进度」就变成了「AI 风险」。**对策：用文本特征定位（找含「下一步：」的那个 td），不要硬编码列索引**。
4. **展开区在另一个 `tr` 里** —— `tr.ant-table-expanded-row`，与主行不是同一个元素。在主行 `tr` 上找展开区的按钮会误命中主行自己的按钮（我就误点到了「查看核验详情并确认」）。

## v2.21 识别工作台：点击外部收起 + 收起图标优化

用户两条反馈：① 「在进行智能识别的时候，我希望点击左侧的页面，右侧的智能识别就能自动缩进」；② 「收起按钮前面的图标太丑了，换一个」。

### 一、根因

`src/components/RecognitionDrawer.tsx` 的 `Drawer` 显式配了 **`mask={false}`** —— antd 在不渲染遮罩层时**也不会绑定「点击外部 → onClose」**，所以点左侧列表毫无反应（完全对上用户描述的「点了没反应」）。

用户两个决策：① **不加遮罩、点了就收起**（左侧视觉与现在完全一致）；② 图标换**向右双箭头**。

### 二、改法

```tsx
// 改前
mask={false}
styles={{ body: { paddingTop: 12 } }}

// 改后 —— 遮罩「存在但完全不可见」
styles={{
  mask: { background: 'transparent' },
  body: { paddingTop: 12 },   // 原有条目必须合并保留
}}
```

- **`styles.mask` 是 antd 原生语义 DOM 键**（Drawer 自 5.13.0 起支持）→ 无需 `rootClassName` + 全局 CSS 覆写，无新增样式文件、无全局副作用。`tsc` 直接通过即是类型层面的确认。
- **图标**：`MinusOutlined` → `DoubleRightOutlined`；抽屉自右滑入、收起即向右滑出，方向语义最准。import 保持字母序。`MinusOutlined` 在本文件仅此一处使用，替换安全。
- **收起入口统一**：点外部 / 底栏「收起」/ 标题栏 `×` / `Esc` 四者都走 `CLOSE_RECOGNITION` —— **状态层与数据流零改动**。

### 三、不扩散（本轮边界）

| 组件 | 配置 | 本轮处理 |
|---|---|---|
| `RecognitionDrawer` | 原 `mask={false}` | **唯一改动点** |
| `ExpressImportDrawer` | 未设 mask（默认可见遮罩） | 不动 —— 它本来就能点外部关 |
| `FullscreenModal` | `maskClosable={false}` | **必须保持** —— 四个全屏明细弹窗靠它防误触丢草稿 |

全项目只有 `RecognitionDrawer` 一处用 `mask={false}`。

### 四、点击语义（已向用户说明）

**不可见遮罩会消费掉该次点击** —— 点左侧列表的第一下只用于收起工作台，不会穿透触发那一行的点击 / 展开 / 行内按钮。这是标准抽屉交互，也避免「想关抽屉却误开了某个弹窗」。实测确认无弹窗被误开。

### 五、踩坑（本轮新增/复现）

- **`search_content` 的 `count` 模式会漏报**：对确实已写入 `<br>` 的内容报 0 命中（上一轮 v2.21 就复现过一次）。**核对应优先用 `read_file` 读该行**，不要只用 `search_content` 判定。
- **shell 会在 cmd 与 PowerShell 之间切换**：同一会话里 `cd /d "..."` 与 `Set-Location '...'` 可能只有一个能用。命令报「找不到位置形式参数」即说明当前是 PowerShell，改用 `Set-Location`。
- 4 字的「最小化」不再受 antd 给两字按钮插空格的影响，实测选择器比原来的「收 起」更稳。
